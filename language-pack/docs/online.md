# 在线交换

在线交换让相隔两地的两名玩家连接起来：每块开发板都与自己的主机进行本地交换，两个 App 再通过公共 Nostr 中继传递各自主机提供的宝可梦，中继只能看到加密事件。代码：`pokeldn/online/`；启动器参数 `--online` 与 `--online-code`。

## 房间

两个 App 在运行同一款游戏并使用同一密码时相遇：

    room = sha256("pokeldn online 1|<game>|<code or 'open'>")     64 hex digits

配对的版本共用同一个游戏键（`frlg`、`sv`）。游戏中自带连接密码时，就使用主机自己的连接密码。同一张桌子上的两台主机可以直接找到彼此；若要在同一张桌子上测试，请给每台主机各自的本地密码，并用 `--online-code` 让两块开发板进入同一个房间。

## 中继

每个事件都是临时（ephemeral）kind 21059 的 NIP-01 事件，带有 `["t", <room>]` 标签，并且对某个 App 还带有 `["p", <its signing key>]` 标签。每个 App 从启动前 10 s 起订阅带该房间标签的 kind 21059 事件，向每个中继发布，并丢弃重复的事件 ID。每个会话都用一把全新的 secp256k1 密钥签名（BIP-340，`pokeldn/online/schnorr.py`）。

| 中继 | 8 个事件，每 2 s 一个 |
|---|---|
| relay.primal.net, relay.snort.social, offchain.pub, relay.nostr.net, nostr.oxtr.dev, nostr-pub.wellorder.net | 8 个全部送达；默认集合 |
| relay.damus.io | 送达 4 个，随后封禁该地址一段时间 |
| nos.lol, nostr.mom | 无（受速率限制） |
| nostr.wine | 拒绝（付费） |

`POKELDN_RELAYS`（逗号分隔的 URL）会替换默认集合。offchain.pub 会拒绝未知密钥的突发请求，只接受限速发送的事件。第二个 App 的消息到达 0.4 s 后，两个 App 完成配对；344 字节的记录约 0.15 s 传输完毕。

### 已存储事件

在 relay.primal.net、relay.nostr.net、nostr.oxtr.dev、nos.lol、nostr.mom、offchain.pub 与 nostr-pub.wellorder.net 上测得：

| 事件 | 结果 |
|---|---|
| 来自全新密钥 | 被接受并回送 |
| 带有 NIP-40 `expiration` 的 30402 | 到期前提供，到期后不再提供 |
| 以相同 `d` 重新发布的 30402 | 一分钟内只提供较新的那个 |
| 指名某个 30402 的 kind 5 | 一分钟内只提供该 kind 5 |
| 仅通过 `a` 地址指名被替换的 30402 的 kind 5 | 五台丢弃；nostr.oxtr.dev 与 nostr-pub.wellorder.net 会保留，直到某个 kind 5 指名它自己的 id |
| 无 `expiration` 的 30402、kind 5 与 kind 1059 | 17 天后仍全部提供 |
| 指名某个 kind 1059 的 kind 5 | 六台提供 1059 的中继全部丢弃 |
| 通过其 `p` 密钥读取 kind 1059 | 六台提供；relay.nostr.net 要求 AUTH 并拒绝 |

## 会合

每个事件的内容都以 `sha256("pokeldn room key|" + room)` 为密钥使用 AES-256-GCM 加密。

| 消息 | 发送 | 内容 |
|---|---|---|
| `here` | 每 2.5 s，发往房间 | 协议 1、X25519 密钥、训练家名称、App 版本、忙碌状态 |
| `invite` | 发往某个 App | 训练家名称 |
| `yes` / `no` | 应答 | 训练家名称 |
| `bye` | 发往非伙伴 | 原因 |

App 只会邀请看到时间最长、且签名密钥大于自身的空闲 App，一次只邀请一个，最长持续 6 s，在此期间对其他邀请一律回答 `no`。被拒绝或无人应答的邀请会让该 App 在 10 s 内被跳过。伙伴发来的第一条通道消息即视为它的 `yes`。

## 通道

伙伴消息在房间密钥层内还带有发送方的 X25519 密钥，并以如下值再套一层 AES-GCM 加密：

    sha256("pokeldn pair|" + room + "|" + sorted("<signing key>:<x25519 key>" of both) + shared secret)

每条消息都带有 `s`（自身序号）与 `a`（按序收到的最高序号）。未确认的消息每 2 s 重发一次；确认在到达后 0.3 s 发出；ping 每 4 s 一次。伙伴静默 45 s 即视为掉线，若尚未提供任何记录，则会被替换。

| 消息 | 含义 |
|---|---|
| `hello` | 训练家名称与 App 版本，仅一次 |
| `offer` / `withdraw` | 第 *r* 次交换：本地主机提供此记录（base64），或已收回 |
| `accept` / `unaccept` | 第 *r* 次交换：本地主机已确认，或已收回确认 |
| `refused` | 第 *r* 次交换：接收方拒绝了发送方的记录，并说明原因 |
| `done` | 第 *r* 次交换完成；下一次为 *r* + 1 |
| `ping`, `bye` | 保活；离开 |

## 传输的内容

只传输提供的记录与交换状态。PKHeX 会在主机看到收到的记录之前进行检查（`pokeldn.online.session.checker`）：

| PKHeX 发现 | 该记录 |
|---|---|
| 无法解析、校验和错误、种类或形态在该游戏中不存在、id 超出该游戏的数据表 | 拒绝，并向发送方显示原因 |
| 未解禁的道具或招式（《剑》的道具止于 1607） | 拒绝 |
| 任何其他合法性标记 | 照常提供，并向接收方显示该标记 |

## 在启动器中

带 `--online` 的主机端启动器会提供伙伴主机的记录。本地主机提供的记录以 `offer` 发出；伙伴的记录则被提供给本地主机；只有两台主机都确认后，启动器才会确认；`done` 会从盒子开始下一次交换。

| 游戏 | 启动器的提供 | 主机收回自己的提供 | 启动器收回自己的提供 | 启动器的确认 |
|---|---|---|---|---|
| 火红／叶绿 | 伙伴的同行宝可梦区块（三个 200 字节区块，邮件 220，缎带 40），随主机自身的对应区块到达而逐个发送；带伙伴光标的 `SET_MONS_TO_TRADE` | `READY_CANCEL_TRADE`（应答为 `PLAYER_CANCEL_TRADE`）、`REQUEST_CANCEL` | `PLAYER_CANCEL_TRADE` | `START_TRADE` |
| Let's Go | 带伙伴 232 字节记录的 kind 2，用于应答主机的步骤 | 撤回投票（状态 2）、离开（状态 4） | 无 | 在所提供克隆上发送 A 2，末尾字设为 2 |
| 剑／盾 | 20030，带盒子命令 1；0x84 快照的同行栏位保留主机自己的宝可梦 | 盒子命令 2（提供）、5（确认） | 盒子命令 2 | 盒子命令 4 |
| 晶灿钻石／明亮珍珠 | 0x13，应答主机的消息 | 0x45 `{1}` | 0x45 `{1}` | 0x21 `{0, 2}`；安全阶段保持自动 |
| 传说 阿尔宙斯 | 选择器 4，在对应计数器下应答主机发出的同一选择器；已知伙伴记录后，用该记录应答选择器 2 的展示 | 选择器 6 | 无 | 对应主机选择器 5 的镜像操作 |
| 朱／紫 | 带伙伴 348 字节主体的 kind 2 | kind 4 `8000040100` | kind 4 | kind 3 |
| 传说 Z-A | 先给出伙伴选定的预览，再在 0.5 s 后发送该选定 | `0103` | 在下一轮中发送的 `0103` | `0102`，随后 `0104` |

《火红》与《叶绿》会交换整支同行队伍。每一方都会暂存自己的区块，直到伙伴主机发来相同的一对区块；主机等待时不设超时 [trade.c:1478]。只有当 PKHeX 能读取区块中的每只宝可梦时，该区块才会发到主机。光标以 `pick` 的形式先于记录传输。

伙伴离开或静默 45 s 即视为收回提供，除非交换已过不可回头点。火红或叶绿的主机在伙伴离开后，每次选择都会收到 `PLAYER_CANCEL_TRADE` [trade.c:1712]；进行到一半的同行宝可梦交换会以空队伍结束。在《剑》中，交换的记录即内容 50 的记录（[《剑》的交换](swsh_trade.md)）。

## GTS

GTS 让从未同时在线的玩家之间交换存放于银行的宝可梦：玩家从[银行](gui.md#the-bank)上架一只宝可梦，以最多三种想要的种类、一个等级范围以及可选的异色要求作为交换条件；另一位玩家用自己的一只宝可梦应答；上架者的 App 下次打开时完成交换。代码：`pokeldn/online/gts.py`、`pokeldn/app/gts.py`，以及 App 的 GTS 页面。

| 事件 | kind | 签名者 | 内容 |
|---|---|---|---|
| 上架 | 30402（NIP-99），`d` 为随机 id | 每个上架项目一把密钥 | JSON：协议 1、游戏、PKHeX 读出的宝可梦、记录的 SHA-256、`wants` 与 `also`（见下文）、训练家名称、状态、中选提案 |
| 提案 | 1059，`p` 为上架密钥 | 每个提案一把密钥 | 密封内容：上架的 `d`、游戏、记录、训练家名称 |
| 应答 | 1059，`p` 为提案密钥 | 上架密钥 | 密封内容：提案 id 与上架的记录，或拒绝及原因 |
| 删除 | 5（NIP-09） | 被指名事件的密钥 | 无 |

上架项目带有 `pokeldn-gts` 标签，并对每个想要的种类带有 `pokeldn-gts-has-<species>` 与 `pokeldn-gts-wants-<species>` 标签，携带 NIP-99 的 `title`、`summary`、`status`、`published_at`，并在 30 天后过期（NIP-40）。密封主体使用 AES-256-GCM，密钥为 `sha256("pokeldn gts|" + x)`，其中 x 为 ECDH 的 x 坐标（`schnorr.shared_x`）。每个已存储事件的 id 与签名都会被校验。

一个想要条件是 `{"species", "name", "min_level", "max_level"}`，当只接受异色应答时再加上 `"shiny": true`。`wants` 存放第一个；`also` 仅在条件多于一个时出现，最多再放两个，提案只要匹配其中任意一个即为应答。这两个字段都是协议 1 的新增内容：0.40.0 或更早版本的 App 会忽略它们，把上架项目显示为只要求它的第一个想要条件；而它发出的提案若不符合异色要求，会被上架者的 App 拒绝并退回。

| 步骤 | 发生的事 |
|---|---|
| 存入 | 宝可梦必须合法；它会移出银行，上架项目随之发布 |
| 提案 | 宝可梦合法，且符合某一想要条件的种类、等级与异色要求；它会移出银行，并以该上架密钥密封；一个 App 对每个上架项目只持有一个等待中的提案，该上架项目在收到上架者 App 的应答前仍对其他玩家的提案开放；页面会以时钟标记它 |
| 上架者的 App 打开 | 已存储的提案按最早优先依次应答；第一个有效的会被交换，其余被拒绝 |
| 一次交换 | 应答携带上架的记录；上架项目以“已交换”状态重新发布；收到的记录存入银行 |
| 提案者的 App 打开 | 记录会对照上架的 SHA-256 校验后存入银行；若被拒绝、竞争失败或上架项目已撤回，则退回自己的宝可梦；随后删除其提案 |
| 上架项目结束 | 30 天后其宝可梦退回；提案的宝可梦会在结束一小时后、中继已发出所有已存储的应答后退回 |
| 下架 | 以“已撤回”状态重新发布；其宝可梦退回；此后的提案会被拒绝 |

每个上架项目与提案都是 `Documents/pokeldn/GTS`（设置了 `POKELDN_DATA` 时位于 `POKELDN_DATA/GTS`）中的一个文件夹，内含 `state.json`（密钥、已签名事件、已发送的应答）与记录。应答会在发布前写入，每个仍然有效的事件都会重发给每个连接上的中继。已完成的文件夹会在 60 天后删除。一轮大约耗时 30 s。

所用中继与[已存储事件](#stored-events)相同；`POKELDN_GTS_RELAYS` 可将其替换。被修改过的 App 可以扣下本应换出的宝可梦，或上架一只自己并不拥有的宝可梦；SHA-256 只能在事后揭示这一点。没有可信第三方时，公平交换无法实现（Pagnia 与 Gaertner，1999）。

## 未解决

- 中继在 24 小时之后会保留事件多久，以及无过期时间的事件会保留多久。
- 当主机端在主机仍持有自己的提供时将其收回，主机会如何应答：《剑》的盒子命令 2（在确认画面开团的《剑》在命令 1、2 之后 4 s 开始离开）、《朱》的 kind 4、Z-A 的 `0103`、《晶灿钻石》在主机选定后发送的 0x45。Let's Go 与《传说 阿尔宙斯》则会保持等待。
- Z-A 是否接受没有预览的选定，以及《传说 阿尔宙斯》是否接受第二次选择器 4。
- 零售版主机在盒子处等待伙伴的时间，在超过一分钟之后还有多久。
